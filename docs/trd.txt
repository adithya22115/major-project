Technical Requirements Document (TRD)
Project: MediCycle – Smart Medicine Donation & Redistribution Platform
Version: 1.2
Prepared For: Major Project (Updated)

1. Purpose
This Technical Requirements Document defines the technical architecture, technology stack, system components, APIs, database, security, deployment strategy, and development standards for MediCycle, reflecting the current implemented features.

2. System Architecture
Client (React + Vite + Tailwind CSS)        │ HTTPS REST APIs        │Spring Boot Backend        │Service Layer        │Repository Layer (JPA/Hibernate)        │PostgreSQL Database        │Local File System (uploads/) + Cloudinary (optional)
                                                     │
                                                     │Pincode Lookup Service (external API)
                                                     │File Upload Service

3. Technology Stack
Frontend
- React 19, Vite, Tailwind CSS, React Router, Axios
- State Management: React Context (AuthContext)
- Form Handling: React Hook Form (optional)
- UI Components: Custom reusable components
- Icons: Lucide React
- State Persistence: localStorage (JWT token)

Backend
- Java 21, Spring Boot 3.2.x
- Spring Data JPA, Hibernate ORM
- Spring Security (JWT-based authentication)
- Lombok (reducing boilerplate)
- SpringDoc OpenAPI 3 (Swagger UI)
- Validation: Hibernate Validator (Bean Validation 2.0)
- File Upload: Apache Commons FileUpload / Spring Multipart
- External API Integration: RestTemplate for pincode lookup
- Email (future): JavaMailSender

Database
- PostgreSQL 15+ (production)
- H2 Database (development/testing)

Authentication & Security
- JWT (JSON Web Token) for stateless authentication
- Refresh token pattern (optional)
- BCrypt password hashing (cost factor 12)
- Role-Based Access Control (RBAC) with Spring Security
- CORS configuration (allowing frontend origin)
- HTTP Security Headers (X-Frame-Options, CSP, etc.)
- Input validation and sanitization
- Encryption at rest (configuration for future)

Storage
- Medicine images: Local filesystem (uploads/ directory) with organized subdirectories
- Prescription files: Same as medicine images
- Verification documents: Same
- Optional Cloudinary integration (configurable via application.properties)
- File size limits: 5MB per file, 10MB per request
- Allowed types: JPG, PNG, PDF (images), PDF (prescriptions/verification docs)

API Documentation
- SpringDoc OpenAPI automatically generates Swagger UI at /swagger-ui.html
- API versioning via path (/api/v1/... future)
- Detailed operation descriptions, request/response examples

Additional Services
- PincodeLookupService: Integrates with external API (e.g., India Post PIN code API) to validate and suggest city/state from pincode
- FileService: Handles file upload, validation, storage, and retrieval
- GeoService: Utilities for distance calculation (future)

4. Frontend Requirements
- Responsive web design (mobile-first, breakpoint: 640px)
- Role-based dashboards (Donor, Recipient, Pharmacy/NGO, Admin) with dynamic menu rendering
- Reusable components (Button, Input, Card, Modal, Toast, Table, etc.)
- Form validation (client-side using React Hook Form or custom hooks)
- Image upload preview with drag-and-drop support
- Search and filtering (debounced input, multi-select chips)
- Pagination for medicine listings (server-side preferred)
- Role-based route protection (React Router v6 + AuthContext)
- Toast notifications (react-hot-toast or similar)
- Loading states and skeletons
- Error boundaries and fallback UI
- Accessibility (ARIA labels, keyboard navigation)
- Environment variables (VITE_API_BASE_URL)

5. Backend Requirements
- RESTful API architecture with clear resource naming
- Layered architecture (Controller → Service → Repository → Entity)
- Global exception handling (@ControllerAdvice)
- DTO-based request/response (separate internal entities from API contracts)
- Role-based authorization using @PreAuthorize and custom security expressions
- Audit logging via AspectJ or custom annotation (@AuditLog)
- Pagination and sorting support (Spring Data Pageable)
- Efficient querying (JPQL, Criteria API, Projections)
- Transaction management (@Transactional)
- Caching (future: Redis for frequent queries)
- Health check endpoints (/actuator/health)
- Metrics and monitoring (Micrometer, Prometheus)
- Internationalization (i18n) ready (future)
- Async processing (future: @Async for email notifications)

6. Database Tables (Current Schema)
users
  id (BIGSERIAL PK)
  name (VARCHAR NOT NULL)
  email (VARCHAR NOT NULL UNIQUE)
  phone (VARCHAR)
  password (VARCHAR NOT NULL)
  role_id (BIGINT FK -> roles.id NOT NULL)
  address (VARCHAR)
  city (VARCHAR)
  state (VARCHAR)
  pincode (VARCHAR)
  is_verified (BOOLEAN DEFAULT FALSE)
  created_at (TIMESTAMP)
  updated_at (TIMESTAMP)

roles
  id (BIGSERIAL PK)
  role_name (VARCHAR NOT NULL UNIQUE) -- DONOR, RECIPIENT, PHARMACY, ADMIN

medicines
  id (BIGSERIAL PK)
  medicine_name (VARCHAR NOT NULL)
  manufacturer (VARCHAR)
  category (VARCHAR)
  dosage (VARCHAR)
  description (VARCHAR)
  requires_prescription (BOOLEAN DEFAULT FALSE)

medicine_donations
  id (BIGSERIAL PK)
  donor_id (BIGINT FK -> users.id NOT NULL)
  medicine_id (BIGINT FK -> medicines.id NOT NULL)
  quantity (INT NOT NULL)
  batch_number (VARCHAR)
  manufacture_date (DATE)
  expiry_date (DATE)
  item_condition (VARCHAR) -- renamed from 'condition' (SQL reserved word)
  status (VARCHAR DEFAULT 'PENDING') -- PENDING, UNDER_REVIEW, APPROVED, REJECTED, DISTRIBUTED, EXPIRED
  remarks (VARCHAR)
  created_at (TIMESTAMP)
  -- Note: pincode/location now derived from donor's address or separate location entity (future)

medicine_images
  id (BIGSERIAL PK)
  donation_id (BIGINT FK -> medicine_donations.id NOT NULL)
  image_url (VARCHAR NOT NULL)
  image_type (VARCHAR) -- e.g., 'MAIN', 'PACKAGING', 'EXPIRY_CLOSEUP'

prescriptions
  id (BIGSERIAL PK)
  user_id (BIGINT FK -> users.id NOT NULL)
  doctor_name (VARCHAR)
  hospital_name (VARCHAR)
  file_url (VARCHAR)
  issued_date (DATE)
  -- Note: linked to user, can be referenced by medicine_requests

verification
  id (BIGSERIAL PK)
  donation_id (BIGINT FK -> medicine_donations.id NOT NULL)
  verified_by_id (BIGINT FK -> users.id NOT NULL)
  verification_date (TIMESTAMP)
  result (VARCHAR) -- APPROVED, REJECTED
  remarks (VARCHAR)

verification_tokens (email verification)
  id (BIGSERIAL PK)
  token (VARCHAR NOT NULL UNIQUE)
  user_id (BIGINT FK -> users.id NOT NULL)
  expires_at (TIMESTAMP NOT NULL)
  used_at (TIMESTAMP)

inventory
  id (BIGSERIAL PK)
  medicine_id (BIGINT FK -> medicines.id NOT NULL UNIQUE)
  available_quantity (INT DEFAULT 0)
  reserved_quantity (INT DEFAULT 0)
  distributed_quantity (INT DEFAULT 0)
  expired_quantity (INT DEFAULT 0)
  updated_at (TIMESTAMP)

medicine_requests
  id (BIGSERIAL PK)
  recipient_id (BIGINT FK -> users.id NOT NULL)
  medicine_id (BIGINT FK -> medicines.id NOT NULL)
  requested_quantity (INT NOT NULL)
  prescription_id (BIGINT FK -> prescriptions.id)
  status (VARCHAR DEFAULT 'PENDING') -- PENDING, APPROVED, REJECTED, COMPLETED
  approved_by_id (BIGINT FK -> users.id)
  created_at (TIMESTAMP)
  processed_at (TIMESTAMP)

notifications
  id (BIGSERIAL PK)
  user_id (BIGINT FK -> users.id NOT NULL)
  title (VARCHAR NOT NULL)
  message (VARCHAR(1000))
  type (VARCHAR) -- e.g., 'DONATION_APPROVED', 'REQUEST_REJECTED', 'SYSTEM_ALERT'
  is_read (BOOLEAN DEFAULT FALSE)
  created_at (TIMESTAMP)

audit_logs
  id (BIGSERIAL PK)
  user_id (BIGINT FK -> users.id) -- nullable for system actions
  action (VARCHAR NOT NULL)
  entity_name (VARCHAR)
  entity_id (BIGINT)
  timestamp (TIMESTAMP)

7. Core REST APIs
Authentication
POST /api/auth/register          -- User registration (Donor/Recipient/Pharmacy/Admin)
POST /api/auth/login             -- Login returns JWT
POST /api/auth/refresh           -- Refresh token (future)
POST /api/auth/verify-email      -- Verify email with token
POST /api/auth/forgot-password   -- Password reset initiation
POST /api/auth/reset-password    -- Password reset with token
POST /api/auth/change-password   -- Change password (authenticated)

Medicines (Admin)
GET    /api/medicines            -- List all medicines (paginated)
GET    /api/medicines/{id}       -- Get medicine by ID
POST   /api/medicines            -- Create new medicine (Admin)
PUT    /api/medicines/{id}       -- Update medicine (Admin)
DELETE /api/medicines/{id}       -- Delete medicine (Admin)

Donations (Donor/Guest)
POST   /api/donations            -- Create a donation (multipart/form-data with files)
GET    /api/donations            -- Get donations (filtered by user role: donor sees own, pharmacy sees pending, admin sees all)
GET    /api/donations/{id}       -- Get donation by ID
PUT    /api/donations/{id}/cancel-- Cancel donation (donor only, if pending)

Verification (Pharmacy/NGO/Admin)
GET    /api/verification/pending -- Get pending donations for verification
PUT    /api/verification/{id}    -- Update verification result (approve/reject) with remarks
GET    /api/verification/{id}    -- Get verification details

Inventory (Pharmacy/NGO/Admin)
GET    /api/inventory            -- Get inventory summary (paginated, filter by medicine name/category)
GET    /api/inventory/low-stock  -- Get medicines below threshold (future)
POST   /api/inventory/restock    -- Manual stock adjustment (admin)

Requests (Recipient/Pharmacy/NGO/Admin)
POST   /api/requests             -- Create a medicine request (with optional prescription upload)
GET    /api/requests             -- Get requests (filtered by user role: recipient sees own, pharmacy sees pending for their inventory, admin sees all)
GET    /api/requests/{id}        -- Get request by ID
PUT    /api/requests/{id}/cancel -- Cancel request (recipient only, if pending)
PUT    /api/requests/{id}/approve-- Approve request (pharmacy/ngo/admin)
PUT    /api/requests/{id}/reject -- Reject request (pharmacy/ngo/admin)

Notifications
GET    /api/notifications        -- Get user's notifications (paginated)
PUT    /api/notifications/{id}/read -- Mark notification as read
PUT    /api/notifications/read-all -- Mark all as read
DELETE /api/notifications/{id}   -- Delete notification

Admin
GET    /api/admin/dashboard      -- Dashboard statistics (donations, requests, users, inventory)
GET    /api/admin/users          -- Manage users (list, filter, role update, status toggle)
GET    /api/admin/medicines      -- Manage medicines (same as /api/medicines but admin-only)
GET    /api/admin/verifications  -- Verification history and stats
GET    /api/admin/reports        -- Generate reports (future)

Utility
POST   /api/pincode/lookup       -- Validate pincode and get city/state (calls external API)
POST   /api/upload/file          -- Generic file upload (used by frontend for doctor's prescription, etc.)

8. Security Requirements
- JWT Authentication with access token expiration (15 min) and refresh token (optional)
- HTTP-only cookies for token storage (future) OR localStorage with XSS protection
- Role-Based Access Control (RBAC) enforced at method level with @PreAuthorize
- Input validation using javax.validation annotations (@NotNull, @Size, @Pattern, @Email)
- Output encoding to prevent XSS (Spring MVC auto-escapes in Thymeleaf, but for JSON API ensure proper content-type)
- CSRF protection disabled for stateless API (rely on SameSite cookies if using cookies)
- Rate limiting (future: Bucket4j or Spring RateLimiter)
- Secure headers configured via Spring Security
- Dependency scanning (OWASP Dependency-Check)
- Regular dependency updates
- Environment-specific configuration (application-{profile}.properties)
- Secrets management: never commit application.properties; use environment variables or vault
- CORS: restrict to trusted origins in production
- File upload validation: size, type, virus scanning (integration point)

9. Performance Requirements
- Login Response: <2 seconds
- Medicine Search: <1.5 seconds (with indexing)
- Image Upload: <5 seconds (depending on file size)
- Dashboard Load: <2 seconds
- API Response Time: 95% of requests <1s (excluding file upload)
- Database Query Optimization: proper indexing on foreign keys, search columns
- Pagination: default page size 20, max 100
- Caching: future use of @Cacheable for static data (medicines, roles)

10. File Upload Requirements
- Supported: JPG, JPEG, PNG, PDF
- Maximum Size: 5 MB per file
- Maximum Request Size: 10 MB (multipart)
- Storage: Local filesystem under /uploads/{entity}/{id}/ (e.g., /uploads/donations/123/)
- File Naming: UUID + original extension to avoid collisions and path traversal
- Virus Scan: placeholder for integration with ClamAV or similar (future)
- Image Processing: optional thumbnail generation (future)
- Access Control: files served only via authenticated endpoints that check permissions
- CDN Integration: ready for Cloudinary or AWS S3 via configuration switch

11. Logging & Monitoring
- Structured Logging (JSON format) using Logback/SLF4J
- Log Levels: ERROR, WARN, INFO, DEBUG
- Log Categories:
  * Auth: login attempts, registration, token validation
  * Donation: creation, status change, file upload
  * Verification: approval/rejection actions

  * Request: creation, approval, rejection
  * User: role changes, status updates
  * System: startup, shutdown, scheduled tasks
  * Error: exceptions with stack trace
- Log Retention: configurable (e.g., 30 days)
- Monitoring:
  * Health checks (actuator)
  * Metrics: request count, duration, error rates
  * Alerts: on error rate spikes, response time degradation
- Log Shipping: future integration with ELK stack or cloud logging

12. Testing Strategy
- Unit Testing (Services, Utilities, Controllers with @WebMvcTest)
  * Frameworks: JUnit 5, Mockito, AssertJ
  * Coverage Target: 80%+ for service layer
- Integration Testing (REST APIs with @SpringBootTest + Testcontainers)
  * Real PostgreSQL instance via Testcontainers
  * Test scenarios: full workflows (donation → verification → request)
- Frontend Testing
  * Unit: Jest + React Testing Library for components and hooks
  * Integration: Cypress for end-to-end user flows
  * Snapshot testing for UI regression
- User Acceptance Testing (UAT)
  * Test plans covering all user roles
  * Bug tracking and resolution
- Performance Testing (future)
  * Load testing with JMeter or k6
  * Stress testing for peak usage
- Security Testing
  * OWASP ZAP scans
  * Penetration testing (before production deployment)

13. Deployment
- Frontend → Vercel (or Netlify)
  * Environment variables: VITE_API_BASE_URL
  * Build command: npm run build
  * Output directory: dist
- Backend → Render (or AWS Elastic Beanstalk, Google Cloud Run)
  * Build: Maven package
  * Start: java -jar target/midicycle.jar
  * Environment variables: SPRING_PROFILES_ACTIVE=prod, DATABASE_URL, JWT_SECRET, etc.
- Database → Neon PostgreSQL (or AWS RDS, Google Cloud SQL)
  * Connection string via environment variable
  * Enable SSL, automated backups
- Additional Services
  * Pincode Lookup: external API (no deployment needed)
  * File Storage: local disk on backend instance (ensure persistence) or cloud storage (S3/Cloudinary)
- CI/CD Pipeline (future)
  * GitHub Actions: build, test, deploy on push to main
  * Staging and production environments
  * Database migration scripts (Flyway or Liquibase)
- Infrastructure as Code (future)
  * Terraform or AWS CloudFormation for reproducible deployments
